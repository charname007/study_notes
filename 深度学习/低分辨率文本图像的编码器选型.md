# 低分辨率文本图像的编码器选型

## 一句话总结

低分辨率文本的核心矛盾是：**信息本来就少，编码器的下采样会再丢一次**。所以选型的第一原则不是「用更强的 backbone」，而是**控制空间压缩比，别把仅有的笔画信息压没**。

## 为什么低分辨率文本对编码器特别敏感

自然图像分类里，一路下采样到 1/32 是常规操作——猫的耳朵丢几个像素无所谓。

但文本不一样：**一个字的信息量集中在笔画上**。LR 下一个字符可能只有 4–5 个像素宽，再经 1/16 或 1/32 下采样，笔画直接糊成一团。

这也解释了为什么 SVTRv2 要把特征高度分辨率**从 $H/16$ 翻倍到 $H/8$**——原文说 SVTR 的做法「对规则文本有效，但难以保留不规则文本的独特特征」。[2]

## 一、按「空间压缩比」给编码器分类

这是最实用的划分维度。文本图像的宽高比通常很大（32×128 甚至 32×512），所以**高度方向压得越狠越致命**。

| 编码器类型 | 高度压缩比 | 代表 | 适用 |
|---|---|---|---|
| **无下采样 / 浅** | 1× | 9×9 Conv 单层（TATT 图像分支） | 已对齐的文本行 |
| **仅压高度** | 1/4 ~ 1/8 | SVTR / SVTRv2 | **文本识别的主流选择** |
| **多分辨率并行** | 1/4 ~ 1/32 全程保留 | HRNet | 需保留细节 + 多尺度 |
| **逐步下采样** | 1/16 ~ 1/32 | ResNet、U-Net | 通用骨干，低分辨率下吃亏 |

## 二、六种具体选择

### ① SVTR 式：patch embedding + 三阶段 height merging

**最贴合文本的编码器设计**。把图切成小块（原文叫 character components，因为每块可能只含一个字的一部分），然后三阶段里**只压高度、不压宽度**。[1]

核心组件是 local / global mixing block：local 抓笔画级局部模式，global 建字与字之间的长程依赖，形成「多粒度字符感知」。[1]

**为什么适合低分辨率**：高度被压到 1/4 而非 1/16/1/32，笔画的纵向结构保住了。而且它把整个序列建模融进了视觉模型，不需要额外 RNN。[1]

后续工作普遍拿 SVTR 当默认编码器底座（如 CPPD 直接用它提取特征）。[7]

### ② SVTRv2 式：进一步保住高度分辨率

在 SVTR 基础上做了两件对低分辨率直接相关的事：[2]

**特征高度翻倍**：$H/16 \to H/8$。理由是原分辨率难以保留不规则文本的独特特征。[2]

**多尺寸缩放（MSR）**：按宽高比 $R=W/H$ 分四档（$R<1.5$、$1.5\text{–}2.5$、$2.5\text{–}3.5$、$R\ge3.5$），分别 resize 到 $[64,64]$、$[48,96]$、$[40,112]$、$[32,\lfloor R\rfloor\times32]$。[2]

**这条最值得记住**：传统做法把所有文本强行拉到 32×128，对窄文本（竖排、短词）会造成**严重形变**；原文报告 MSR 在第一档上比固定 32×128 **提升 15.3%**。[2]

### ③ HRNet 式：全程保留高分辨率

HRNet 的设计哲学正是「**不是从低分辨率恢复高分辨率，而是全程维持高分辨率**」——多个分辨率分支并行，反复做跨分辨率信息交换。[3]

有工作把它用在 STR 上，做双分支解码（SR 分支 + 识别分支），且 **SR 分支只在训练时用、测试时丢弃**，以控制推理成本。[3]

**适合低分辨率的理由**：没有池化层，细粒度空间信息不会被不可逆地丢掉。

**但要注意**：这条路线在 STISR 主流里并不流行，参数和显存代价明显。

### ④ Transformer / 自注意力式：建长程依赖

TATT 的 TP Interpreter 就是个典型：Encoder 用**多头自注意力**处理文本先验，Decoder 用**多头交叉注意力**把语义对齐到空间位置。[6]

**它解决的不是「保分辨率」而是「全局关联」**：卷积是局部算子，抓不住旋转/弯曲文本的大位置偏移；注意力可以让每个图像位置直接查询文本语义。[6]

**代价**：TATT 自己承认全局注意力使复杂度随文本长度增长。[6]

### ⑤ Criss-Cross 注意力式：折中方案

TATSR 用 **Criss-Cross Transformer Blocks**，即只在行、列方向上做注意力，而非全图全局注意力。[4]

**动机**：全全局注意力对文本这种「横向排列」的结构是浪费，十字交叉能在保持长程建模的同时降低复杂度。[4]

对低分辨率文本尤其合适——因为文本的长程依赖**主要沿水平方向**。

### ⑥ BLSTM 增强的残差块（SRB）

TSRN 的做法：在残差块里插入**双向 LSTM**，把特征图按水平线展平成序列，用 BLSTM 建模序列依赖。[5]

而且它用了**水平 + 垂直两个方向**的 BLSTM，以应对倾斜文本。[5]

**这是 STISR 里最经典的「为文本定制」编码器设计**，其消融显示 5 个 SRB 相比 SRResNet 提升 4.9%。[5]

## 三、选型决策表

| 你的情况 | 推荐 | 理由 |
|---|---|---|
| 文本已矫正、横向排列，追求精度 | **SVTR / SVTRv2** | 只压高度，笔画结构保住 |
| 文本宽高比差异大、有竖排或极短词 | **SVTRv2 + MSR** | 避免强行 resize 造成的形变 |
| 需要保留细节给小目标/密集文字 | **HRNet 多分辨率** | 全程高分辨率，不丢空间细节 |
| 文本有旋转/弯曲形变 | **Transformer（TATT 式）/ 十字注意力** | 局部算子抓不住大位置偏移 |
| 做 STISR（先超分再识别） | **SRB（BLSTM 残差块）** 或 **U-Net** | 序列建模 + 像素级重建都要 |
| 算力受限 | **浅层 Conv 起步**，别急着上大 backbone | 低分辨率输入本身信息少，大模型容易过拟合 |

## 四、四条设计原则

**① 优先控制高度压缩比，而非堆深度。** 文本的判别信息沿宽度排列，高度压太狠是主要损失来源。[1][2]

**② 别强行统一 resize。** 32×128 是历史惯性，按宽高比分桶（MSR）能带来两位数提升。[2]

**③ 长程依赖沿水平方向，不需要全全局注意力。** 十字交叉或条带注意力是更经济的折中。[4]

**④ 编码器要能被「文本先验」查询。** 若下游要用识别器给先验，编码器输出必须保留空间坐标语义，否则对齐无从谈起。[6]

## 五、常见误区

**① 以为「更强 backbone = 更好」。** 在低分辨率文本上，ResNet-152 往往不如精心设计的浅层 + height-merging 结构，因为后者保留了笔画分辨率。

**② 忽略宽高比分布。** 同一套 resize 策略对 32×128 和 32×512 的文本效果完全不同。[2]

**③ 把 SR 编码器和识别编码器混为一谈。** STISR 的编码器要重建像素（需细节），识别的编码器要出语义（需压维度），目标不同。TATT 就明确分成图像特征分支和 TP Interpreter 两条。[6]

**④ 全局注意力不加约束。** 文本长度一长，$O(N^2)$ 会爆。[6]
